# ops-drill-kit

我在 VMware 里搭了一个能反复弄坏、也能反复修好的运维靶场。

起因很实际：学运维最难的一步是"练习排障"，但手上没有生产环境，也不敢拿别人的机器试。云主机能买，可一旦把 MySQL 的 binlog 玩坏了，重建成本比练习成本还高。所以我用快照做底座——弄坏了回滚，修好了留证，重来一次几十秒。

靶场里复刻了 13 类故障：Linux 4 类、MySQL 4 类、网络 4 类、综合 1 类。每一类都要求四件事同时成立：**能注入、能定位、能恢复、能判题**。

## 三个数字

| | |
|---|---|
| **13** | 类故障，覆盖 Linux / MySQL / 网络 / 综合 |
| **4** | 个案例有完整证据链和 SHA-256 指纹，可以逐条核对 |
| **1** | 套判题机制：不靠我说"修好了"，靠 boot / unit / invocation / PID 四个标识把同一轮日志串起来 |

## 最难的不是造故障，是证明它真的发生过

第一版做出来的时候，我发现自己陷入一个循环：注入脚本跑完，我看日志，觉得"应该是成功了"，然后写进文档。这个"应该"很危险——日志里有 AVC，不代表这次启动被拒；端口起来了，不代表是被我改的那份配置起来的。

所以后来把重心从"制造故障"挪到了"判定故障"。以 L02 为例，一条 SELinux 拒绝必须三样东西同时对上：

```
type=AVC      ... denied { name_bind } for pid=<pid> scontext=...:httpd_t:s0 tclass=tcp_socket
type=SYSCALL  ... pid=<pid> success=no exe="/usr/sbin/nginx"
type=SOCKADDR ... saddr=<被拒绝的地址族与端口>
```

三行的 `pid` 必须相同，`exe` 必须指向同一个二进制，再叠上同一 boot 与 unit 的时间窗。少一样就判 `PENDING`，不判通过。

判题的判定标准是我定的，它由系统执行，不由我执行。这是我在这六天里花时间最多、也最值的一部分——它让"我觉得行了"变成"系统说行才算行"。

## 靶场结构

```
Windows 宿主机
└── VMware Workstation
    └── Rocky Linux 9.8（实验机，带 /etc/opsdrill-lab 标记）
        ├── Nginx ────────── 8080 网关，反代 orderguard-api
        ├── orderguard-api ── FastAPI，:8000
        ├── MySQL 8.4 LTS ─── :3306 回环，业务库 + 影子库
        ├── /var/lib/opsdrill/events.jsonl ── 事件流水（root 保护）
        └── /var/backups/opsdrill/ ────────── 每轮证据目录
```

业务侧是一个最小订单服务：5 条合成订单起步，影子库另放 50 万条合成订单用于性能和恢复实验。数据全是造的。

统一入口是 `bin/opsdrill`：`start` → `check` → `resolve` → `reset`。每轮一个 `run_id`，后续动作必须带 `--expect-run-id`，身份不符就拒绝，不猜着清理。变更类演练带 120 秒或 180 秒 watchdog，超时自动收口。

## 13 类故障

| 编号 | 故障 | 注入方式 | 深度 |
|---|---|---|---|
| L01 | inode 耗尽 / deleted-open | 私有 64 MiB ext4 loop 镜像写满 | 事件齐 |
| L02 | SELinux 端口拒绝 | 独立 transient Nginx 绑未授权端口 | **深度案例** |
| L03 | I/O 压力 | 受控 cgroup 限速模拟 | 模拟，非硬件故障 |
| L04 | 文件描述符上限 | 压低 `LimitNOFILE` 后压连接 | 事件齐 |
| M01 | 索引不可见 | 切换索引 `VISIBLE` 属性 | **深度案例** |
| M02 | 行锁与死锁 | 并发事务制造 1213 | 夹具 + 实机 |
| M03 | 连接耗尽 | 8 条连接占满隔离实例（1040） | 事件齐 |
| M04 | 误删 | 全备 + binlog 回放到误删前 | **深度案例** |
| N01 | DNS 解析失败 | 隔离命名空间改解析器 | 事件齐 |
| N02 | ACL 拦截 | nft 规则丢弃流量 | 事件齐 + 180 s watchdog |
| N03 | 502 / 504 | 停上游 / 开受控慢接口 | **深度案例** |
| N04 | 临时端口耗尽 | 短连接堆积 TIME_WAIT | 事件齐 |
| C01 | 综合故障 | 多故障叠加，有限窗口采样 | 有限窗口，PARTIAL |

"深度案例"指有完整链路：注入、定位、恢复、判题、指纹五项齐全，可以逐条核对。"事件齐"指有实机事件记录，但没有做到四项全闭环。这个区别我写在表里，不含糊。

## 一次真实的失败

M04 做到 v3 的时候，出现了一个很隐蔽的问题。

流程是：启动隔离实例 → 备份 → 更新 → 误删 → 回放 → 停止实例 → 写入"已完成"状态。run `8e1c0b8aab9a0587` 在停止实例之后、写入状态之前出了问题：systemd 把临时 unit 回收了。

于是复位逻辑卡住——它要核对 `InvocationID` 才能确认"这确实是我这一轮启动的实例"，但 unit 没了，ID 取不到。控制器拒绝认定复位完成，状态悬在 `RESETTING`。

这不是功能写错了，是我没考虑到"资源消失"和"状态记录"之间存在时间差。真实的系统崩溃、断电、OOM killer，都会撞上这个窗口。

v4 的改法是：unit 被回收时，不再依赖 `InvocationID` 单点判断，而是要求五个条件同时成立才继续复位——本轮身份匹配、同一启动周期、PID 1 有对应的调用 ID 启停记录、进程与 cgroup 消失、socket 不存在。日志不可用或证据不全，一律拒绝。

改完在 run `4a6cbe2782b24e0b` 复现了同样的中断点，复位返回 `STOPPED`，两个实例停止、业务 readiness 200 独立核验。

这个 bug 教我的事：只看状态机不看实际资源，会漏掉悬空态。状态说"我在停止中"，但资源早就没了——这种情况不靠状态判断，靠现场判断。

## 关于工具

这套系统的命令，大量由 AI 编码工具执行。我不打算绕开这件事，但我想说清它意味着什么。

正因为执行快了，验证才必须更严。所以我把力气几乎全花在判题和留证上：每一轮操作都要过身份核验、日志关联、摘要比对，通不过就不算数。工具跑得再快，也过不了我自己设的判题关。

分工是这样的：故障假设、方案取舍、失败判定标准、验收条件由我定；命令下发、日志抓取、重复性核对交给工具。

证据里有个 `actor` 字段，取值 `user` 或 `agent`，标的是命令下发通道，不是决策归属。本仓库的 run 都是 `agent`。
