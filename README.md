# ops-drill-kit

一台能被弄坏、也能被修好的运维靶场。

在 VMware 隔离虚拟机里复刻 13 类运维故障——Linux 4 类、MySQL 4 类、网络 4 类、综合 1 类。每一类都要求四件事同时成立：**能注入、能定位、能恢复、能判题**。判题不靠自述，靠 boot、unit、invocation、PID 四个标识把同一轮日志串起来，证据落 SHA-256 指纹。

它解决的是"想练排障但不敢在生产上练"这个问题。靶场是快照驱动的：弄坏了回滚，修好了留证，重来一次的成本只有几十秒。

四个案例有完整链路，可以直接读：

| 案例 | 故障 | 一眼能看懂的结果 |
|---|---|---|
| [L02](docs/cases/01-L02-SELinux端口拒绝.md) | SELinux 拒绝 Nginx 绑定端口 | 19081 起不来，切 8443 起来，全程 Enforcing，没动策略 |
| [N03](docs/cases/02-N03-网关502与504.md) | 网关 502 / 504 | 双变体跑通，首次 504 因缺 drop-in 失败，失败记录保留 |
| [M01](docs/cases/03-M01-索引失效.md) | 索引不可见导致查询退化 | 50 万行，平均 30.55 ms → 0.84 ms，指纹一致 |
| [M04](docs/cases/04-M04-误删与时间点恢复.md) | 误删后按 binlog 回放 | 订单 100/200 → 101/200，应用直读恢复库 200 |

## 靶场结构

```
Windows 宿主机
└── VMware Workstation
    └── Rocky Linux 9.8（实验机，带 /etc/opsdrill-lab 标记）
        ├── Nginx ────────── 8080 网关，反代 orderguard-api
        ├── orderguard-api ── FastAPI，:8000
        ├── MySQL 8.4 LTS ─── :3306 回环，业务库 + 影子库
        ├── /var/lib/opsdrill/events.jsonl ── 事件流水（root 保护）
        └── /var/backups/opsdrill/ ────────── 每轮证据目录
```

业务侧是一个最小订单服务：5 条合成订单起步，影子库另放 50 万条合成订单用于性能和恢复实验。所有数据都是造的，不含任何真实客户信息。

## 13 类故障

| 编号 | 故障 | 注入方式 | 判题关联 |
|---|---|---|---|
| L01 | inode 耗尽 / deleted-open | 私有 64 MiB ext4 loop 镜像写满 | unit + invocation |
| L02 | SELinux 端口拒绝 | 独立 transient Nginx 绑未授权端口 | boot + unit + PID |
| L03 | I/O 压力 | 受控 cgroup 限速模拟 | unit + 事件 |
| L04 | 文件描述符上限 | 压低 `LimitNOFILE` 后压连接 | unit + PID |
| M01 | 索引不可见 | 切换索引 `VISIBLE` 属性 | 执行计划 |
| M02 | 行锁与死锁 | 并发事务制造 1213 | run_id + 事务 ID |
| M03 | 连接耗尽 | 8 条连接占满隔离实例（1040） | run_id |
| M04 | 误删 | 全备 + binlog 回放到误删前 | run_id + 结果指纹 |
| N01 | DNS 解析失败 | 隔离命名空间改解析器 | unit + invocation |
| N02 | ACL 拦截 | nft 规则丢弃流量 | unit + 180 s watchdog |
| N03 | 502 / 504 | 停上游 / 开受控慢接口 | request ID + timing 日志 |
| N04 | 临时端口耗尽 | 短连接堆积 TIME_WAIT | run_id + 连接统计 |
| C01 | 综合故障 | 多故障叠加，有限窗口采样 | 有界判题 + 窗口 |

统一入口是 `bin/opsdrill`：`start` → `check` → `resolve` → `reset`，每轮一个 `run_id`，后续动作必须带 `--expect-run-id`。身份不符就拒绝，不猜着清理。变更类演练带 120 秒或 180 秒 watchdog，超时自动收口。

## 判题与留证

判题靠关联，不靠断言。以 L02 为例，一条拒绝要三样东西同时对上：

```
type=AVC      ... denied { name_bind } for pid=<pid> scontext=...:httpd_t:s0 tclass=tcp_socket
type=SYSCALL  ... pid=<pid> success=no exe="/usr/sbin/nginx"
type=SOCKADDR ... saddr=<被拒绝的地址族与端口>
```

三行的 `pid` 必须相同、`exe` 必须是同一个二进制，再叠上同一 boot 与 unit 的日志时间窗，才算"这一轮真的被拒了"。少一样就判 `PENDING`，不判通过。

每轮结束后，结果文件单独算 SHA-256 落在证据目录里。文档里每个关键结论都带 run_id 或摘要，`sha256sum` 对上就说明是同一次运行。

## 分工与方法

方案设计、故障假设、失败判定、验收标准由我确定。命令执行、日志抓取、重复性核对交给会话工具。工具的输出同样要过 SHA-256 与判题关联，通不过就重跑。

事件记录里有 `actor` 字段，取值 `user` 或 `agent`，标的是命令下发通道，不是决策归属。本仓库的 run 都是 `agent`。

## 素材边界

仓库只收文字材料与源码候选，不含原始聊天、凭据、数据库转储、虚拟机文件。源码来自候选包的 `source.tar.gz`，不含外层安装包与原 Git 历史。

敏感信息扫描覆盖文件名匹配与常见密钥模式，18 个文件命中，逐个人工复核上下文，未确认真实凭据；未覆盖二进制内容与图片 OCR。这一步只能降低风险，不能证明零风险。

更早的 v27 安装包、v41 之前的中间版本，与本仓库的 v41 候选不是同一份东西，结论不互通。
