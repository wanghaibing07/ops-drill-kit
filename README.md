# ops-drill-kit · 运维故障演练靶场

我用六天，在一台虚拟机上复刻了 13 类运维故障。其中 4 类做到了从注入到判题的完整闭环。

## 我是谁，为什么做这个

大二专科在读，方向是计算机网络与云计算，想找 DevOps / SRE 方向的实习。

做这个东西的起因很具体：练排障没地方练。生产环境不敢动，云主机弄坏了重建成本比练习成本还高，学校课程给的多是"配置成功"的路径，很少给"配置错了怎么找回来"的路径。

一开始我以为最难的是把服务搞挂。结果不是——搞挂只要五分钟。真正难的是证明它真的挂过、真的修好了。

这个认知改变了整个项目的走向，也解释了为什么下面有一半篇幅在讲"怎么判定"，而不是"怎么注入"。

## 四个案例

| 案例 | 故障 | 结果 | 关键动作 |
|---|---|---|---|
| [N03](docs/cases/02-N03-网关502与504.md) | 网关 502 / 504 | 双变体跑通；**首次 504 做成了 404** | 按失败归档，不重跑算通过 |
| [L02](docs/cases/01-L02-SELinux端口拒绝.md) | SELinux 拒绝 Nginx 绑端口 | 19081 起不来，切 8443 起来，全程 Enforcing | 不加端口例外，换端口 |
| [M01](docs/cases/03-M01-索引失效.md) | 索引不可见导致查询退化 | 50 万行，**30.55 ms → 0.84 ms** | 不 DROP，改 INVISIBLE |
| [M04](docs/cases/04-M04-误删与时间点恢复.md) | 误删后按 binlog 回放 | 订单 **100/200 → 101/200**，应用直读恢复库 200 | v3 有缺陷，返工成 v4 |

> 第一次做 504，我做出来的是 404。那次失败我没删。

## 判题为什么难

注入脚本跑完，我看日志，觉得"应该是成功了"，然后写进文档。这个"应该"很危险——日志里有 AVC，不代表这次启动被拒；端口起来了，不代表是被我改的那份配置起来的。

所以判题要求多个标识交叉对齐。以 L02 为例，一条 SELinux 拒绝必须三样东西同时成立：

```
type=AVC      ... denied { name_bind } for pid=<pid> scontext=...:httpd_t:s0 tclass=tcp_socket
type=SYSCALL  ... pid=<pid> success=no exe="/usr/sbin/nginx"
type=SOCKADDR ... saddr=<被拒绝的地址族与端口>
```

三行的 `pid` 必须相同，`exe` 必须指向同一个二进制，再叠上同一 boot 与 unit 的时间窗。

**为什么不是一个标识？** 因为每个都能被单独骗过：PID 会被复用，boot 只说明"开机后发生过"，unit 只能证明服务在跑。四个叠起来，才足以说明"这一轮、这个进程、被这个策略拒了"。

**少一样就判 `PENDING`，不判通过。** 这叫 fail-closed：证据不全时默认失败，而不是默认成功。设计成反过来的话，我会得到一堆"看起来通过"的轮次。

每轮结果另算 SHA-256。它防的是**引用错版本**，不是防伪造：文档里引用的结论和证据文件必须是同一轮的，事后改文档不会让旧结论对上新证据。

真实性不靠哈希，靠判据——同一 boot、同一 unit、同一时间窗的三条记录同时成立。这个伪造不了，因为它要求系统自己产生日志。

## 我否决过的五个方案

面试里会被问"哪些判断是你做的"。下面这五个更省事的方案被我否掉了，每一个都有当时记录的痕迹：

**1. 不给 19081 加 SELinux 端口例外，换端口。**
一条 `semanage port -a` 就能让服务起来。不加，因为靶场要可重建——例外规则会留在镜像里，下次做同类实验分不清"策略本来允许"还是"我上次加的"。

**2. 不用 `DROP INDEX` 制造索引失效，改 `INVISIBLE`。**
DDL 非事务型，进程被杀时索引可能删了也可能没删，恢复时要靠猜。属性切换可逆、可判、可重复，代价是模拟不完全等价——这个代价我写在 runbook 里了。

**3. 不把 404 那一轮重跑一遍算通过，归档为失败。**
重跑一次大概率能过，记录上也好看。但那样就丢掉了"新机会缺 drop-in"这个真实缺陷，也不会去补 v41 bootstrap 里的文件核验。

**4. 审计拒绝后不放宽审计脚本，走受控续接。**
11-13 单表 PITR 因为审计解析 Base64 出错被拦下。改一行判断就能放行。没改——审计的作用就是在不确定时拦住流程，为了跑通去放宽它，等于把保险丝换成铜丝。改法是保留失败账本，另起账本记录续接过程。

**5. 不手动调 watchdog 交差，等满 180 秒自然触发。**
第一次 L02 在 InvocationID 写入前注入异常，手动调起 watchdog 也能拿到记录。但那只能证明 watchdog 逻辑对，证明不了定时器接得对。第二次等满三分钟，让 systemd 自己触发。

这五个决定的共同点：**更省事的方案被我否掉了。**

## 靶场结构

```
VMware Workstation
└── Rocky Linux 9.8（实验机，带 /etc/opsdrill-lab 标记）
    ├── Nginx ────────── 8080 网关，反代 orderguard-api
    ├── orderguard-api ── FastAPI，:8000
    ├── MySQL 8.4 LTS ─── :3306 回环，业务库 + 影子库
    ├── /var/lib/opsdrill/events.jsonl ── 事件流水（root 保护）
    └── /var/backups/opsdrill/ ────────── 每轮证据目录
```

业务侧是最小订单服务：5 条合成订单起步，影子库另放 50 万条合成订单用于性能和恢复实验。数据全是造的。

统一入口 `bin/opsdrill`：`start` → `check` → `resolve` → `reset`。每轮一个 `run_id`，后续动作必须带 `--expect-run-id`，身份不符就拒绝，不猜着清理。变更类演练带 120 或 180 秒 watchdog，超时自动收口。

## 13 类故障，做到什么程度

| 编号 | 故障 | 结果 |
|---|---|---|
| L02 · N03 · M01 · M04 | 见上表 | **闭环：注入 → 定位 → 恢复 → 判题 → 指纹** |
| L01 | inode 耗尽 / deleted-open | 实机事件齐，判题关联到 unit + invocation |
| L03 | I/O 压力 | 受控模拟，非真实硬件故障 |
| L04 | 文件描述符上限 | 实机事件齐 |
| M02 | 行锁与死锁 | 真实 1213，夹具 + 实机双验证 |
| M03 | 连接耗尽 | 真实 1040，业务 API 联合端到端未做 |
| N01 | DNS 解析失败 | 正常流程 + 一次 supervisor 异常恢复 |
| N02 | ACL 拦截 | 控制器、复位、180 秒 watchdog 已验证 |
| N04 | 临时端口耗尽 | 正常流程 + 单次中断恢复 |
| C01 | 综合故障 | 三个有限窗口采样，普通检查仍为 PARTIAL |

铺 13 类不是为了让数字好看。是为了验证同一套机制在不同类型的故障上都能工作——系统层、网络层、查询层、恢复层。机制跑通了，剩下的类是复用，不是重做。

## 验证到哪一步

**已验证**：四个场景的完整链路，各有 run_id 与结果摘要；v27 曾在空盘机完成 bootstrap，19 项基线通过。

**部分验证**：其余九类有实机事件，但未做到五项闭环；有的停在有限窗口，有的只做了夹具。

**明确未做**：v41 整包的空盘安装（v30–v41 安装器有变更，v27 的结论不能继承，所以现在不能说"能一键部署"）；云端 CI 从未运行；断电与跨重启恢复没测——**所以这套东西不能用于评估真实灾备能力**。

## 下一步

按优先级：

1. **把 L02 和 N03 搬到 kind 上，用 Chaos Mesh 重做一遍**。虚拟机里的 SELinux 和 systemd 语义，容器里没有；反过来容器里的网络策略和 Pod 生命周期，虚拟机也没有。同一类故障在两个环境里的可观测面完全不同，我想把这个差异测出来。
2. 补 v41 的空盘安装验证。现在这个包别人拿去装不上。
3. 跨重启恢复——目前最大的技术空白。
4. 九类补齐五项闭环。
