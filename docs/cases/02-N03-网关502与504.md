# N03：Nginx 网关 502/504 故障注入与恢复验证

## 验证摘要

两个变体最后都跑通了。但第一次 504 没成立——不是超时，是 404，原因是少了一个 drop-in 文件。

## 环境与故障条件

- 新空盘机，从安装包 bootstrap
- 链路：Nginx `:8080` → 反代 → `orderguard-api` `:8000` → MySQL
- 502 变体：停掉实验订单 API，网关拿不到上游
- 504 变体：开启本轮受控慢接口 `/api/v1/orders/slow`，约 12 秒返回
- 控制器给每轮注册 120 秒 systemd 看门狗；504 的门控开关另有最长 120 秒单调时钟有效期

## 首次注入失败：404 与 504 根因区分

起服务，开门控，请求慢接口：

```bash
curl -i --max-time 5 http://127.0.0.1:8080/api/v1/orders/slow
```

返回 404。

**404 与 504 对应不同故障阶段。**

504 的意思是"网关等上游超时"，前提是上游有这条路、只是慢。404 的意思是"这条路不存在"。Nginx 在等一个不存在的上游路径，`proxy_read_timeout` 设 10 秒还是 100 秒，结果都是 404，永远不会变成 504。

查 systemd 单元：

```bash
systemctl cat orderguard-api
```

缺 `40-opsdrill-n03.conf`。

这个 drop-in 负责把慢接口的路由开关挂上去。没装，应用启动时就没注册 `/api/v1/orders/slow` 这个路由。所以门控文件写了也没用——路由压根不存在，门控开的是空气。

## 失败归档与缺陷处理

单纯重试不能解决新机缺少 drop-in 的安装缺陷，也无法解释首次返回 404 的原因。因此保留原失败事件，并将配置文件创建与校验纳入 v41 bootstrap。

失败任务按以下方式归档：

- 失败状态归档在 `/var/backups/opsdrill/N03/failed-start-archive-f96990034f868371/`
- 失败事件保留在事件流水里
- 按同一 run ID 安全复位（不是猜着清理）
- 控制器确认环境干净后，再协调 CLI 状态

这一轮在文档里记为失败，不能算"故障验证成功"。计数上它占一轮，证据上它是一条有价值的记录。

## 修复之后，两步验证不能反

补上固定的门控环境配置，重启实验 API。然后：

1. `curl http://127.0.0.1:8080/ready` → 200，业务链正常
2. 不开门控时请求慢接口 → 仍是 404

**第二步是关键。** 如果补完文件、404 消失了，那说明不清 404 是被门控控制的，还是文件本来就没装上。只有"文件装了、门控没开、仍然 404"，才能证明 404 是门控的正常表现，而不是又一个配置缺失。

该检查用于区分受控门控行为与配置缺失，验证慢接口的访问状态由本轮开关控制。

## 验证

补装之后，分别跑两个变体：注入 → 故障期 check → 恢复 → 恢复后 check → 同轮复位。

关联证据分两层，强度不同：

| 证据 | 关联方式 | 强度 |
|---|---|---|
| 响应 request ID ↔ 独立 timing 日志 | 按 ID 精确关联 | 强 |
| 错误日志 ↔ 请求时间窗 | 按时间窗口关联 | 弱 |

错误日志里没有与响应相同的 request ID，所以只能按窗口关联。这个区别写进了 runbook，不混着说成"日志全部对应"。

两次响应的 request ID 分别与独立 timing 日志对上；错误日志在各自有限窗口内，分别记录了连接拒绝和上游超时。

## Nginx 超时语义

`proxy_read_timeout` 限制的是**相邻两次读之间的等待**，不是整个请求的绝对时长。

所以"12 秒慢接口 + 10 秒 read_timeout = 504"这个说法不严谨。真正决定的是：在这 10 秒里，上游有没有吐出过任何字节。如果上游持续吐一点数据、每次间隔都不超过 10 秒，请求可以跑几分钟都不超时。

该语义差异直接影响 504 超时条件的判断。

## 异常处置与工程改进

一次完整的失败轮次，加补装、加重跑。

收益是 v41 bootstrap 里加了固定文件的创建与核验：已有相同文件保留，遇到冲突、不安全目录、符号链接就拒绝。还补了测试——创建、幂等、冲突拒绝、符号链接、调用顺序。

**这个修复比案例本身更有价值**：它把"新机第一次会缺文件"从一个偶发问题，变成了安装器会主动拦住的问题。

## 工程结论

**失败记录用于推动安装流程修复。** 将缺失 drop-in 的错误转化为安装器中的显式创建与核验步骤，降低新环境重复出现同类问题的概率。

## 验证范围

- 只覆盖本机两个有限请求，不代表所有 502 / 504 的成因
- 虚拟机挂起与重启后的行为未验收
- 开关过期只表示应用不再接受它，不保证文件已删除；看门狗和 reset 各自负责清理，不互相替代
- 运行中的请求不会因开关关闭而立即取消

## 验证入口

```bash
sudo bin/opsdrill status
sudo bin/opsdrill start N03 --variant 502
sudo bin/opsdrill check N03 --expect-run-id RUN_ID
sudo /usr/bin/python3 -I -B /usr/local/libexec/opsdrill/n03/n03_502.py resolve RUN_ID
sudo bin/opsdrill check N03 --expect-run-id RUN_ID
sudo bin/opsdrill reset N03 --expect-run-id RUN_ID
```

有效故障的 check 返回 1，环境或状态不符返回 2。没有活动故障验证时，check 不代表通过。
