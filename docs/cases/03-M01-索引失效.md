# M01：50 万行，30.55 ms 到 0.84 ms

## 一句话

同一条查询、同一份数据、同一个环境，只把一个索引调成不可见，平均延迟从 30.55 ms 降到 0.84 ms。SQL 一个字没改。

## 现场

- 影子库 `orderguard_stage3`，50 万条合成订单
- 固定查询：按商户 + 状态 + 创建时间过滤，带分页
- 目标索引：`orders.idx_merchant_status_created`
- 业务主库仍在原库，影子库只用于性能和恢复实验

## 我否决的方案：不用 DROP INDEX

演练要制造"索引不存在"的等效效果，两条路：`DROP INDEX`，或者把索引设为 `INVISIBLE`。

选后者。

DDL 不是事务型的。`DROP INDEX` 执行到一半进程被杀，索引可能已经删了、也可能还在，没有回滚可用。恢复时要靠独立查询确认最终状态，而"确认"这一步本身就可能出错——看到一个不存在的索引，你分不清是删成功了还是本来就没有。

`ALTER TABLE ... ALTER INDEX ... INVISIBLE` 是可逆的属性切换：状态明确、可判定、可复位、可以重复执行。它只改优化器能不能看见这个索引，不动物理结构。

代价是它不够"真"——严格说 INVISIBLE 和不存在不完全等价。所以 runbook 里写清楚：这是等效模拟，不是物理删除。

## 怎么测的

预热 10 次，测量 50 次。两组跑同一段基准代码，记录查询参数与结果指纹。

预热是为了排除冷缓存的影响。如果第一组跑在冷缓存上、第二组跑在热缓存上，测出来的是缓存差异，不是索引差异。

结果指纹是为了证明两组查的是同一批数据。哈希一致，说明"数据没变，只有索引可见性变了"，变量被控制住了。

| 指标 | 索引不可见 | 索引可见 |
|---|---|---|
| 平均延迟 | 30.55 ms | 0.84 ms |
| 中位数 | 29.85 ms | 0.84 ms |
| 预热 / 测量 | 10 / 50 | 10 / 50 |

中位数和平均数都降了两个数量级，不是个别样本拉低平均。

## 判题看什么

不看 `SHOW INDEX`，看执行计划。

```sql
EXPLAIN <固定查询>
```

判"索引生效"的唯一依据是 `key` 是否命中目标索引、`rows` 估算是否合理。

`SHOW INDEX` 里有一行，不代表优化器用了它——可能统计信息过期、可能选择性判断走了别的路、可能 `key` 是 NULL。这个区别做过一次对照：历史性能实验是"从无索引到建索引"，当前 CLI 是"隐藏已有索引"。两者都能让延迟变化，但不是同一件事。文档里分开写，不合并成一个"M01 完成"。

## 一条自我限制：全局参数一条都不动

演练只碰索引可见性。以下参数全程不动：

- `slow_query_log`
- `long_query_time`
- `log_output`
- `log_queries_not_using_indexes`
- `local_infile`

注入前记录它们的全局值，复位时逐项比对。

**如果发现外部漂移，只报告、不改回。** 这条也是否决：贸然改回可能覆盖别人的变更，制造新问题。理由是分不清是谁改的、持久化配置源在 `/etc/my.cnf.d/` 还是 `SET PERSIST`。

这条约束让演练能做的事情变少，但避免了"修好一个故障、顺手改坏三个配置"。

## 恢复与异常

如果注入过程中进程被 SIGKILL 或 VM 崩溃，第一步不是复位，是看现场：

- `/var/lib/opsdrill/m01/state.json` 里的本轮状态
- 当前索引的身份和可见性
- 是否有残留的锁

统一 CLI 持有的轮次必须用同一 run ID 复位。身份不明时保留现场，不能盲目跑旧版独立 reset——那可能作用在错误的对象上。

重启后的保守复位路径有模拟测试，但没做过真实 VM 重启验证。这个缺口写在 runbook 里。

## 这个案例教我的

**控制变量比控制结论重要。** 一开始我只想证明"加索引会变快"，那随便测两组就行了。后来改成"只改一个属性、其他都不动"，才敢说这两个数字之间是因果关系，不是相关。

## 边界

- 数值只适用于本机、本查询、本数据集，不可外推
- 历史建索引实验与当前隐藏索引不是同一实现
- 新版"从无索引到人工建索引"状态机在 1000 行隔离夹具上验过创建、检查、删除、原 schema 恢复；状态机 11 项 + 本地账本 6 项测试有记录
- 但正式 CLI 接线、外部并发 DDL、索引归属、watchdog 行为、跨 VM 重启恢复都还没验
- 早期分页测试的事务快照条件不足，后续需要重测

## 复现入口

```bash
sudo bash drills/mysql/M01/check.sh          # 基线检查
sudo bash drills/mysql/M01/inject.sh --dry-run
sudo bash drills/mysql/M01/inject.sh        # 注入：索引设为 INVISIBLE
sudo bash drills/mysql/M01/check.sh         # 退出 1，故障存在
sudo bash tests/solutions/M01/solution.sh   # 恢复：设为 VISIBLE
sudo bash drills/mysql/M01/check.sh         # 退出 0
sudo bash drills/mysql/M01/reset.sh         # 清理
sudo bash drills/mysql/M01/reset.sh         # 幂等，再跑一次仍成功
```

只在通过 `guard_require_lab` 且 `systemd-detect-virt=vmware` 的实验机上执行。注入期间不要跑 50 次性能基准——那会污染测量。
