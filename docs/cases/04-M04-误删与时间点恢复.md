# M04：MySQL 时间点恢复与业务可读性验证

## 验证摘要

全备 + binlog 回放到误删前。还原后的应用直接读恢复库：全备状态读到订单金额 100、200，回放后读到 101、200。同一进程、同一订单池，两阶段接口都返回 200。

## 环境与故障条件

- 全新 socket-only 合成 source / target，两个隔离 MySQL 实例，不与业务主库共用
- 数据是造的：几笔合成订单，金额可辨认
- 时间点恢复工具：全量备份 + `mysqlbinlog` 回放
- 应用侧：FastAPI 订单服务，8 个非凭据的应用、配置、依赖清单文件

## 数据库与业务接口联合验收

数据库层面说"恢复成功"很容易：表在、行数对、`CHECK TABLE` 通过。但这只证明 SQL 能跑，不能证明业务能用。

真实场景里，恢复失败通常不是因为 binlog 回放错，而是因为：

- 应用配置指向的还是旧实例
- 依赖文件版本跟恢复的数据对不上
- 权限、连接串、环境变量没跟着恢复

所以这一轮的重点不是"数据库回来了"，是"应用读得出来"。

## 做法

四步：

1. **全备**。mysqldump 逻辑备份 source，得到基线状态。
2. **制造变更**。更新两笔订单：100 → 101，另一笔保持 200。
3. **误删**。删掉其中一行，模拟误操作。
4. **回放**。从全备恢复，再用 `mysqlbinlog` 回放到误删前的位置——事务边界之后、删除之前。

然后是最关键的一步：**还原应用并让它自己读**。

备份 8 个明确列出的非凭据文件（应用代码、配置、依赖清单），还原到独立目录，核对每个文件的 SHA-256 与普通权限，用还原后的文件启动独立 FastAPI 进程，连恢复库，调订单接口。

## 结果

| 阶段 | 应用读到的金额 | `/ready` | 订单接口 |
|---|---|---|---|
| 全备状态 | 100、200 | 200 | 200 |
| PITR 之后 | 101、200 | 200 | 200 |

怎么读这张表：

- **101** 说明回放停在了更新之后 —— 事务边界找对了
- **200** 说明另一笔没被动过的订单还在
- **两条都在** 说明删除被回滚掉了，回放位置在删除之前
- **两阶段都 200** 说明应用不是"能连上"，是"能正确查"

三个条件同时满足才算恢复，缺一个都只是"看起来恢复了"。

## 清理也是验证的一部分

恢复做完不算完，还得证明没留下垃圾：

- 测试账号只授目标表的 `SELECT` 权限，不授写权限
- 结束前删除账号，核实删除回执
- 两个隔离实例按身份停止
- 现有业务 readiness 保持 200

权限最小化不是形式。恢复实验里如果给了 `ALL PRIVILEGES`，一旦回放位置算错，误删的可能不只是合成数据。

## 另一轮：50 万行

11-14 做了一次更大规模的验证，但做法不是"重新导入 50 万行"。

用的是 11-13 那个恢复目标——就是那次"审计 Base64 解析失败、修复后受控续接"的目标。目标实例已停止，数据目录完整。

流程：

1. 核验目标实例正常停止、数据目录无符号链接和多重硬链接
2. 逐文件复制并核对摘要，在新 socket-only 实例中打开副本
3. 比对 3 张表的内容摘要 + 4 张表的结构摘要
4. 确认：500,000 条订单，商户 88 有 25,000 条
5. 还原 8 个应用文件，启动隔离应用
6. `/ready` 与订单查询均 200，接口返回的 20 条订单与同一恢复库的只读查询逐项一致

没有重跑导入，也没有修改原恢复目录。这样做的好处是：验证的是"已有的恢复目标能不能被应用正确读取"，而不是"再导入一次能不能成功"。

结果 SHA-256：`c2ec466b7c06b489b9e38ef47e0797bedcac1311377d53b4e2d6b453aef54cdd`

## 审计拒绝与受控续接

11-13 做单表 PITR 时，第一次回放在审计环节断了——审计脚本解析 binlog 里的 Base64 字段出错，恢复流程判定"无法确认边界"，拒绝继续。

当时有个很诱人的做法：改一下审计脚本，把这条判断放宽，让它过。

没这么做。审计的作用就是在不确定时拦住流程，为了跑通去放宽它，等于把保险丝换成铜丝。

处理方式是受控续接：保留原失败账本，另起独立账本记录续接过程，新旧两份账本都在，摘要都不改。

这次失败后来变成了资产——11-14 那一轮 50 万行验证，用的就是这个"经历过失败续接"的恢复目标。比一次顺利跑通的目标更能说明流程经得起中断。

## 异常路径：v3 状态核验缺陷

run `8e1c0b8aab9a0587` 暴露了一个设计缺陷。

目标实例停止后，systemd 把临时 unit 回收了。旧控制器（v3）在复位时想再核对一次 InvocationID——但 unit 已经没了，InvocationID 取不到，于是拒绝认定复位完成。

这一轮不是"自动复位通过"。处理方式是：源实例经本轮身份核对后单独停止，把同一启动周期的 systemd 启停记录、调用 ID、进程、cgroup、socket 全部独立核验一遍，失败账本和归档状态保留。

修复思路是 v4：unit 被回收时，不靠 InvocationID 单点判断，而是要求五个条件同时成立才继续复位：

1. 本轮身份匹配
2. 同一启动周期
3. systemd PID 1 有对应的调用 ID 启停记录
4. 进程与 cgroup 均已消失
5. socket 不存在

日志不可用、证据不全、PID 被复用时，一律拒绝。

验证：新机 run `4a6cbe2782b24e0b` 在停止目标之后、保存完成状态之前模拟中断，CLI 后续复位返回 `STOPPED`，两个实例停止与业务 readiness=200 独立核验。

这个失败比顺利跑通那次更有价值——它说明"停止"和"记录已停止"之间存在一个窗口，窗口内崩溃就会出现"实例没了但状态还在 RESETTING"的悬空态。只看状态机不看实际资源，会漏掉这种悬空。

## 工程结论

**状态字段不等于实际状态。** 状态说"我在停止中"，资源可能早就没了；状态说"已完成"，也可能只是写进去了一行字。判断要靠现场核对，不能只看状态字段。

## 验证范围

- 小型合成数据，不含真实业务数据量级
- 用实验机既有虚拟环境和内存中的连接适配，不是完整运行环境重建
- 不含 SELinux 标签、生产凭据、依赖环境重建
- 跨库 PITR、生产级异机容灾、断电、跨重启——都没覆盖
- 50 万行那轮的 20 条接口结果与总数检查，不等于对完整订单表逐行比对
- 备份与回放的 SQL 逻辑大小限制 16 MiB，不包含数据文件、binlog、文件系统开销，不是总磁盘配额

## 验证入口

```bash
sudo bin/opsdrill start M04
sudo bin/opsdrill check M04 --expect-run-id RUN_ID
sudo bin/opsdrill resolve M04 --expect-run-id RUN_ID
sudo bin/opsdrill reset M04 --expect-run-id RUN_ID
```

入口脚本需要 `--vm-uuid <独立核实的 VM DMI UUID>` 和 `--source-root <可信项目副本>`，并会先验证应用源码、CLI、辅助文件的摘要和目标 VM 身份。错误 UUID 和篡改过的辅助文件都测过：在创建事件之前就被拒绝。

只在授权且空闲的实验机上跑。异常或身份不明时保留本轮账本和资源，不猜着清理。
